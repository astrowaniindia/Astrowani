# iOS Port Plan — Astrowani Customer + Vendor apps

Written 2026-08-24. Status of every claim below: **measured against the repo**, not assumed.
Both apps are React Native **0.77.2**, old architecture (`newArchEnabled=false`).

## 0. The headline findings

**The good news, and it's bigger than expected:**

1. **Both apps already have an `ios/` directory** — generated by `react-native init` and then
   never touched. So there is no "create the iOS project" step; it's a configuration job, not
   a scaffolding job.
2. **You already use EAS Build** for Android (`eas.json`, EAS project id
   `bbdc8460-4b17-4d15-8b78-3ac4288138eb`). EAS builds iOS on Expo's cloud Macs, so
   **this Windows machine is not a blocker for compiling or shipping iOS.** No Mac purchase
   is strictly required.
3. **Your OTA channel works on iOS.** `@hot-updater/react-native` ships a real iOS podspec
   and `ios/HotUpdater` native code. So the JS-only shipping flow you rely on today carries
   over.
4. **The JS is already mostly platform-aware.** Every `PermissionsAndroid` call I checked is
   correctly wrapped in `Platform.OS === 'android'`, and the Android-only native module
   (`CallForegroundService`) is accessed through `utils/callForegroundService.js`, which
   already no-ops on iOS by design.

**The bad news, in order of how much it will hurt:**

| # | Problem | Consequence if shipped as-is |
|---|---|---|
| 1 | **No CallKit / PushKit** | Incoming calls will NOT ring when the app is backgrounded or killed. This is the core product loop. See Phase 4 — this is the one genuinely large piece of new work. |
| 2 | **No `GoogleService-Info.plist` for either app** | Push notifications completely dead on iOS. Needs Firebase iOS apps + an APNs key. |
| 3 | **Customer bundle id is still the template default** `org.reactjs.native.example.$(PRODUCT_NAME)` | Cannot be submitted. |
| 4 | **`AppDelegate.mm` is stock in both apps** | No Firebase init, no notification delegate, no APNs token registration, no URL-scheme handling for Razorpay returns. |
| 5 | **Zero app icons** in either iOS asset catalog (`find ... Images.xcassets -name '*.png'` → 0) | Build rejected at upload. |
| 6 | **`PrivacyInfo.xcprivacy` declares `NSPrivacyCollectedDataTypes` as EMPTY** | Factually wrong — the apps collect phone number, birth data, location, payment info, device id, analytics (PostHog) and crash data (Sentry). Apple validates this against the App Privacy questionnaire. |
| 7 | **Vector-icon fonts were unregistered** | Every icon renders as a blank box. (Fixed — see Phase 1.) |
| 8 | **No entitlements files** | Push capability cannot be enabled. |
| 9 | Vendor `ios/` has no `Podfile.lock` and neither does customer | Pods have never been installed; first `pod install` is where unknown-unknowns surface. |

**Non-issues I checked and cleared** (so nobody spends time on them):
- `patches/` are all Android/Windows NDK CMake workarounds. `apply-native-patches.js` runs on
  `postinstall` and skips cleanly — it will not interfere with an iOS build.
- ATS cleartext: the only `http://` URLs in either app are placeholder Bing image URLs in the
  customer's `screens/Home/Astrologers.js` mock data. One `sed` fixes it. Nothing real is
  cleartext — backend, Supabase, PostHog and Sentry are all HTTPS.
- `otpless-react-native` is a **dead dependency** in the vendor app —
  `startOtpVerification.js` is imported by nothing. No iOS setup needed; candidate for removal.
- `react-native-permissions` is in the customer app's `package.json` but **imported nowhere**.
  It needs no Podfile `setup_permissions!` block today, but see Phase 3.

#### ⚠️ Icon caveat — read before launch

The only source art in the repo is **512×512 with an alpha channel** (`customer_play_store_launcher_icon.png`);
nothing larger exists anywhere (the largest Android asset is a 432px
`ic_launcher_foreground.png`). That art is also unusable as-is on iOS for three reasons:
transparent corners, **pre-baked rounded corners** (iOS applies its own mask, so it renders
double-rounded), and artwork filling only ~60% of the canvas.

What was generated instead: the navy artwork panel was detected by pixel scan
(x 102–408, y 103–408) and made **full-bleed** on a matching navy background, flattened to
opaque `Format24bppRgb` — **no alpha channel, which is itself an App Store rejection
criterion**. Verified: all 9 files opaque, correct dimensions, opaque corner pixels.

This is **correct in format and good enough to build and TestFlight**, but the 1024
marketing icon is a 3.3× upscale and is visibly soft. The App Store product page shows that
icon large. **Export a true 1024×1024 from the original design before public launch** and
drop it in as `icon-1024.png`. The smaller sizes are downscales and look fine.

**Risk note on `project.pbxproj`:** edited by targeted line/regex surgery, since there's no
Xcode here. A full Xcode project/target rename was deliberately NOT attempted — high risk,
zero user-visible benefit, since `CFBundleDisplayName` already controls the home-screen name.
The internal target remaining `AstrologyApp` is cosmetic only.

None of this is code, and Phase 1 doesn't depend on it — but Phase 5 cannot start without it.

2. **Firebase** — add two iOS apps (`com.astrowanicustomer`, `com.astrowaniVendor`) to the

## 4. Phase 4 — Incoming-call reliability (CallKit + PushKit)

**This is the one large piece of genuinely new engineering, and it is not optional for a
consultation marketplace.**

The problem: on iOS a killed or backgrounded app **cannot** be woken reliably by a normal FCM
data push to present an incoming call. Android's socket + FCM + foreground-service combination
has no iOS equivalent. The platform's answer is:

- **PushKit** — a dedicated high-priority VoIP push channel (separate APNs key, separate
  entitlement), which iOS delivers even when the app is killed.
- **CallKit** — the native full-screen incoming-call UI. iOS *requires* that a PushKit VoIP
  push reports a call to CallKit essentially immediately, or it kills the app and eventually
  revokes the privilege.

Work involved:
1. Backend: an APNs VoIP sender alongside the existing FCM path, chosen by device platform.
   Touches the `incoming_call` emit path in `index.js`.
2. Both apps: a CallKit provider bridging to the existing WebRTC accept/reject flow — which
   already has a clean choke point in `utils/incomingRequestActions.js` (vendor).
3. Then, and only then, declare `voip` in `UIBackgroundModes`.

**Recommendation:** treat this as its own phase after a working non-CallKit build exists.
Sequencing it later means we can validate the whole app on iOS first. But **do not ship to
the store without it** — an astrologer app that misses calls when backgrounded will collect
one-star reviews, and CLAUDE.md already records that `missed: 48` vs `rejected: 7` is the
dominant accept-rate problem on Android. iOS without CallKit makes that strictly worse.

### Consequence of "not yet enrolled" — and why it isn't a blocker

An EAS **simulator** build (`ios.simulator = true`, `distribution: internal`) requires **no
Apple account and no signing credentials at all**. So the sequence is:

1. Phases 1 + 3 (config + JS correctness) — now, no account needed.
2. First EAS **simulator** build — no account needed. This is where the pod/compile fight gets
   resolved, and it is the bulk of Phase 5.
3. Enrolment completes → device/TestFlight builds unlock, and only then do we need signing.

That means **the expensive, uncertain part of the port is not gated on the $99 enrolment.**
An `eas.json` simulator profile is therefore part of Phase 1, not an afterthought.

The one caveat: a simulator build cannot validate microphone, camera, real WebRTC media, push
notifications, or Razorpay. Those all need a physical device, so they wait for enrolment.
Everything else — launch, login, navigation, layout, fonts, icons, images, API calls — is
testable without it.
