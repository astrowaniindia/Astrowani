# OTP System — End-to-End Audit (2026-08-18)

Scope: `astrowani-backend` (`/api/users/mobile-otp-request`, `/api/users/mobile-otp-verify`,
`otp_codes`, EnableX SMS), `astrowani_customer-main`, `astrowani_vendors-main`.
Every finding below was verified against the **live** database and the **live**
`backend.astrowani.com`, not inferred from reading code.

> **Note on method:** one probe (`918600638210`, intent=login) returned 200, which means it
> **sent a real OTP SMS to that astrologer's phone**. That was an unintended side effect of
> confirming the duplicate-account bug. No other probe sent an SMS — the rest were the
> reviewer number, invalid numbers, or numbers that 404'd before the send.

---

## TL;DR — why it "works sometimes"

There is no single flaky component. There are **five independent defects**, and each one
produces a different flavour of "the OTP didn't come". Two of them are permanent per-user
lockouts that will never self-heal, which is why it looks random across people rather than
random across time.

| # | Defect | Symptom it produces | Severity |
|---|---|---|---|
| 1 | Phone number normalized for **sending** but never for **identity** | Specific users permanently get **no SMS at all**, plus duplicate accounts | Critical |
| 2 | 8-sends-per-hour cap reachable by a normal frustrated user | "after multiple attempts it stops working" — verbatim | Critical |
| 3 | No timeout on backend→EnableX; 15 s timeout on the vendor app | App says "failed", SMS actually arrives, retry then hits cooldown | High |
| 4 | Country picker is decorative — selection never leaves the app | A non-`+91` selection silently sends to a wrong number | High |
| 5 | `errors.log` is **26 GB**, fed by a self-feeding EPIPE loop | Disk-full → whole backend degrades → recovers on restart | High |

All five are now fixed in code (not yet deployed). **One thing still needs a human: checking
the production VPS disk** — see finding 5. The seven secondary findings below are untouched.

## 1. Critical — the phone number is normalized for sending, but not for identity

> **STATUS: FIXED 2026-08-18** (code not yet deployed). `normalizePhone()` added to
> `index.js`; both OTP endpoints canonicalize on entry. Migration applied to production via
> `scripts/normalizePhoneNumbers20260818.js`. Three rows deliberately left for a human
> decision — see "What was migrated" at the end of this section.

`toE164Strict()` (`index.js`) is called **only** to build the EnableX `to:` field. The **raw**
string from the request body is what gets used for every identity purpose:

- `otp_codes.phone_number` (primary key, and therefore the throttle key)
- `customers.mobile` — both the lookup and the insert
- `astrologers.phone_number` — both the lookup and the insert
- the `phone` claim inside the issued JWT

Meanwhile both apps' `sanitizePhoneInput()` deliberately allows **10, 11, or 12 digits**
(`.slice(0, 12)`), and both Login screens only check `phoneNumber.length < 10`. So
`9876543210`, `09876543210` and `919876543210` all reach the backend as three different
strings that all deliver SMS to the same handset — but are three different *people* as far as
the database is concerned.

### Verified live consequences

**a) A real customer is permanently locked out, and gets no SMS.**

`customers` contains `+919119395097` (Vansh Sharma), stored with a `+91`. When they type their
number normally:

```
POST /api/users/mobile-otp-request {phoneNumber:"9119395097", intent:"login"}
-> 404 {"code":"NO_ACCOUNT","message":"No account found for this number. Please sign up first."}
```

The `intent === 'login'` gate runs **before** the send, so no SMS is ever attempted. This user
cannot log in, and cannot sign up either (signup either 409s or silently creates a second
account, depending on which format they type). This is exactly "no OTP gets sent to us", and it
will never resolve on its own.

**b) One astrologer already has two accounts.**

```
astrologers.phone_number = "8600638210"    (ASTRO shruti)
astrologers.phone_number = "918600638210"  (ASTRO shruti, approval=pending, suspended)
```

Same person, two rows, because the number was entered in two formats. Whichever format they
type decides which account they log into — including which wallet, earnings and session history
they see. There is already a `scripts/mergeDuplicateCustomers20260808.js` in the repo, which
suggests this has bitten before and was patched at the symptom rather than the cause.

**c) Two astrologer accounts can never receive an OTP at all.**

`toE164Strict` rejects anything that isn't `[6-9]\d{9}` after normalization, and the endpoint
400s before sending:

```
phone_number "70388"       -> 400 INVALID_PHONE_NUMBER   (rejected astrologer)
phone_number "1234567890"  -> 400 INVALID_PHONE_NUMBER   (approved: "ansh sharma")
```

Both confirmed live. The strict validator added on 2026-08-16 was correct in itself, but it was
added *in front of* rows created before it existed, with no backfill — so those accounts went
from "works" to "permanently unreachable" on that deploy.

**e) How the bad row actually gets written — and why the fix is only one place.**

Vendor signup no longer inserts into `astrologers` from the app. `VerifyOtp.js` calls
`POST /api/vendor/register`, and that handler deliberately ignores the client-submitted
number, taking it from the verified JWT instead:

```js
const decoded = jwt.verify(...);
...buildVendorRegistrationRow(req.body, decoded.phone)
```

That is the right design — but `decoded.phone` is minted at
`/api/users/mobile-otp-verify` from the **raw** request body. So the un-normalized string
flows: app → verify → JWT claim → `astrologers.phone_number`. This is exactly how
`918600638210` was created.

The useful consequence: because every downstream identity write draws from the JWT claim or
the verify lookup, **normalizing at the two OTP endpoints fixes the entire chain**. There is
no second write path to chase.

(Related: `sql/hardening_02_access_control.sql` still carries a migration note saying
"astrologer registration (VerifyOtp.js) currently INSERTs into this table from the app... Move
registration to a backend endpoint before deploying this". That note is **stale** — the move
already happened. Worth correcting before that file is applied, so nobody blocks on a
prerequisite that is already satisfied.)

**d) The throttle is both bypassable and mis-targeted.** `9876543210` and `919876543210` are
separate rows in `otp_codes`, so the per-number cooldown and hourly cap can be sidestepped by
alternating formats — while a legitimate user who switches format mid-session gets a fresh
budget on one variant and a stale lockout on the other.

### Fix

Normalize **once, at the entry of both endpoints**, and use the normalized value everywhere
downstream:

```js
const phoneNumber = normalizePhone(rawPhoneNumber);   // bare 10 digits
if (!phoneNumber) return res.status(400).json({ code: 'INVALID_PHONE_NUMBER', ... });
```

Then a one-off migration to normalize existing rows: merge the `8600638210` / `918600638210`
pair, and repair `+919119395097`. The two unreachable numbers (`70388`, `1234567890`) need a
manual decision — they are not real mobile numbers.

Store one canonical form. Ten bare digits is the least disruptive choice, since 44 of the 48
existing rows are already in that shape.

### What was actually done

**Code** (`astrowani-backend/index.js`):

- New `normalizePhone()` returns the canonical bare-10-digit form or `null`. `toE164Strict()`
  is now derived from it, so the two definitions cannot drift apart again.
- `/api/users/mobile-otp-request` and `/api/users/mobile-otp-verify` both canonicalize on
  entry and use the result for the OTP row key, the throttle key, the account lookup, and the
  JWT `phone` claim.
- Verify keeps a short-lived fallback to the raw key, so a code requested moments before the
  deploy still verifies instead of returning "No OTP requested for this number". Safe to
  delete 5 minutes (`OTP_TTL_MS`) after deploy.
- `PLAY_STORE_REVIEWER_PHONE` no longer needs its validation bypass — `9999999999` passes
  `normalizePhone` on its own.

**Verified** against a local backend (SMS disabled) pointed at the production database:

| Test | Result |
|---|---|
| `9119395097` login intent | `200` — **was `404 NO_ACCOUNT`** |
| `+919119395097`, `919119395097`, `09119395097`, `+91 91193 95097` | all `429 OTP_THROTTLED` — i.e. they resolved to the **same** row and shared its cooldown, which is the proof of canonicalization |

| Request as `9119395097`, verify as `+91 91193 95097` | `200`, logged into the existing account `d02b966b-…`, JWT `phone` claim `"9119395097"` |
| Customer row count before/after | 15 → 15 — no duplicate created |
| `918600638210` astrologer login | now resolves to the good `8600638210` account |
| `12345`, `1234567890` | still `400 INVALID_PHONE_NUMBER` |
| Reviewer `9999999999` | still `200`, no SMS |

**Migration** (`scripts/normalizePhoneNumbers20260818.js`, dry-run by default, idempotent):

- Applied: `customers.mobile` `"+919119395097"` → `"9119395097"` (Vansh Sharma). That user can
  now log in; before this they could not, in any format.
- **Resolved 2026-08-18** (authorized): deleted the two inert rows below after re-verifying
  each had ₹0 and zero referencing rows at the moment of deletion. `astrologers` went 33 -> 31.

## 2. Critical — a normal frustrated user hits the hourly cap and is locked out

> **STATUS: FIXED 2026-08-18** (code not yet deployed). Limits loosened to 25 sends / 20
> minutes, and the send counter is now refunded when the carrier does not deliver. See "What
> was actually done" at the end of this section.

The knobs in `index.js`:

```js
const OTP_MAX_SENDS_PER_WINDOW = 8;               // per number, per hour
const OTP_RESEND_COOLDOWN_MS   = 45 * 1000;
const OTP_SEND_WINDOW_MS       = 60 * 60 * 1000;
```

The `otp_codes` row — which carries `sends_in_window` — is deleted **only** on successful
verify, on a verify attempt that finds the code already expired, or by the 30-minute purge of
rows expired more than an hour ago.

Now consider the user whose first OTP genuinely didn't arrive (via defect 1, 3, 4, or an
ordinary carrier drop). They tap Resend. The UI timer is 60 s. Eight sends is **about eight
minutes** of ordinary retrying — and it never occurs to them to stop, because nothing has
arrived yet. On the ninth:

```
429 {"code":"OTP_THROTTLED","message":"Too many OTP requests for this number. Please try again later."}
```

They then stay blocked for the remainder of the hour, because `sends_in_window` only resets on
a successful verify — which they cannot do, because they never received a code.

**This is the reported symptom word for word.** The comment above the knobs reasons that "a
human signing up needs one OTP and types it once", which is true only when delivery works. The
cap's failure mode is aimed precisely at the user for whom delivery is already broken.

### Fix

- Raise `OTP_MAX_SENDS_PER_WINDOW`, and shorten `OTP_SEND_WINDOW_MS` to 15–20 minutes so a
  lockout drains in minutes rather than an hour.
- Do not count a send toward the window when the SMS was **not confirmed delivered**.
  `verifyEnxDelivery` already learns this 20 s later and currently only writes a log line.
- Surface `retryAfterSeconds` as a live countdown on the OTP screen. Both apps already adopt it
  into `setTimer`, but the copy still reads "Please try again later", which tells the user
  nothing actionable.

### What was actually done

- `OTP_MAX_SENDS_PER_WINDOW` 8 → **25**; `OTP_SEND_WINDOW_MS` 60 min → **20 min**. A lockout
  now drains in minutes rather than an hour.

  **At 25 this cap is close to non-binding, and that is a deliberate choice.**
  `OTP_RESEND_COOLDOWN_MS` already forces a 45s gap, so the most sends physically possible
  inside a 20-minute window is `1200 / 45 ~= 27`. The cap therefore only trips for someone
  hammering Resend at almost exactly the cooldown boundary for the full 20 minutes — in
  practice the **cooldown**, not this cap, is what limits a single number. The trade accepted
  here is extra SMS spend in exchange for never blocking a real user mid-login. The remaining
  protections are the 45s cooldown, `OTP_MAX_ATTEMPTS` (brute force), and
  `OTP_GLOBAL_HOURLY_CAP` (a spray across many numbers). If SMS spend ever needs reining in,
  lower this number rather than raising the cooldown — the cooldown is what real users feel. `OTP_MAX_ATTEMPTS` is unchanged — that is the
  control that actually stops brute force, and it is keyed to the code rather than the sender.
- **The send counter is refunded when the carrier does not deliver.** `otpStore.set` now
  returns the `last_sent_at` it wrote, and `verifyEnxDelivery` (which already learns the
  delivery outcome 20s later and previously only logged it) calls a new
  `otpStore.refundSend(phone, thatTimestamp)` on any non-delivered status. A send the user
  never received no longer spends their budget — which matters because a run of carrier
  failures is exactly what used to push someone into the lockout.
- The refund is a **compare-and-set on `last_sent_at`**, so if a newer send has replaced the
  row, or the row is gone (verified / expired / purged), it does nothing rather than corrupting
  a counter that no longer belongs to that send.

**Verified** — throttle behaviour driven through the real endpoint against the production
database, by seeding `otp_codes` rows and observing the response:

| Seeded state | Result |
|---|---|
| 9 sends, 5 min into window | `200` — **the old cap of 8 would have blocked this** |
| 15 / 20 / 24 sends | `200` (under the new cap) |
| 25 sends | `429 OTP_THROTTLED` (at the new cap) |
| 25 sends, window 21 min old | `200` — window rolled |
| 15 sends, window 19 min old | `429` under the interim cap of 15; `200` at the final cap of 25 |
| 1 send, 10s ago | `429` — 45s cooldown still enforced |
| 1 send, 50s ago | `200` — cooldown elapsed |
| 25 sends, window 20m01s old | `200` — confirms the lockout drains in 20 min, not 60 |

**Refund** tested separately against real PostgREST (the risk being whether an ISO string
matches a `timestamptz` in a filter — it does): matching timestamp decrements 5 → 4; a stale
timestamp is a no-op; the counter floors at 0; a deleted row is a no-op. 7/7 passed.

## 3. High — timeout mismatch: the app gives up while the SMS is still being sent

> **STATUS: FIXED 2026-08-18** (code not yet deployed). Backend EnableX call capped at 10s;
> both apps now at 20s, with explicit opt-outs for the genuinely slow calls. See "What was
> actually done" at the end of this section.

- `astrowani-backend/index.js` — `await axios.post('https://api.enablex.io/sms/v1/messages/', ...)`
  has **no `timeout`**. The HTTP response to the app is blocked on EnableX.
- `astrowani_vendors-main/src/api/ApiCall.js` — `timeout: 15000`.
- `astrowani_customer-main/src/api/ApiCall.js` — **no timeout at all**.

When EnableX is slow — the exact condition during the carrier congestion that makes OTPs late
in the first place:

- **Vendor app**: aborts at 15 s and shows "Failed to send OTP". The backend carries on, sends
  the SMS, and stores the row. The user gets a code *and* an error. They tap Resend and hit the
  45 s cooldown 429. Indistinguishable from random breakage.
- **Customer app**: no timeout, so the spinner runs indefinitely until the OS drops the socket.

Measured live latency for a real send was 955 ms, so this is a tail-latency problem rather than
a constant one — consistent with "works very good sometimes".

### Fix

Add `timeout: 10000` to the EnableX call, and `timeout: 20000` to the customer app's axios
instance — keeping the client timeout strictly greater than the backend's, so the backend is
always the one that decides. On timeout, delete the stored row so the retry starts clean.

### What was actually done

- **Backend**: `timeout: 10000` on the EnableX send (and `15000` on the delivery-status
  lookup, which also had none). 10s is deliberately below both apps' client timeouts, so the
  **backend is always the party that decides a send failed** and can roll the stored OTP back.
- **Customer app**: `timeout: 20000` added (was unset — the OTP spinner could hang until the
  OS dropped the socket).
- **Vendor app**: `15000` → `20000`, so it can no longer give up before the backend does.

**A regression this nearly introduced.** A blanket 20s on the customer app's shared axios
instance would have newly broken two things that previously relied on having *no* timeout:

- `POST /api/upload-image` — a base64 profile photo is often 1–3 MB, which on Indian mobile
  data easily exceeds 20s. Used at signup (`VerifyOtp.js`) and in `UserProfileScreen.js`.
- `POST /api/astro/:key` — the backend blocks on third-party Jyotisham report generation.

Both now opt out explicitly with `LONG_REQUEST_TIMEOUT_MS` (60s), exported from `ApiCall.js`
with a comment explaining why. The Free Services screens are unaffected either way — they call
the API with bare `fetch`, not the shared instance.

**Verified**: a send failure returns `502` in ~1s **and rolls the stored OTP row back**, so the
retry is clean and no send budget is consumed (tested with deliberately invalid EnableX
credentials, so no SMS could be sent). An axios timeout raises `ECONNABORTED` into that same
catch block, so it takes the same rollback path. Both apps lint clean (0 errors).

## 4. High — the country picker does nothing

> **STATUS: FIXED 2026-08-18** (code not yet deployed). Replaced with a fixed `+91` in both
> apps. See "What was actually done" at the end of this section.

Both Login screens render a working country selector with flags and dial codes:

```js
const [callingCode, setCallingCode] = useState('91');
...
<Text style={styles.callingCode}>+{callingCode}</Text>
```

`callingCode` is **never included in the request body**. The backend hardcodes `+91`. A user who
changes the country sees `+1` on screen while their number is dispatched to an Indian `+91`
number — either bouncing at the carrier, or reaching an unrelated real person.

### Fix

Either send `callingCode` and validate per-country on the backend, or remove the picker and
show a fixed `+91`. Given the DLT template and sender ID are India-only, removing it is the
honest option.

### What was actually done

Removed. Both Login screens now render a non-interactive flag + `+91` instead of a picker, and
the modal, `countryCode` / `callingCode` / `isPickerVisible` state, `togglePicker`,
`selectCountry`, the `countries` import and the imports they orphaned (`Modal`, `FlatList`,
`Icon`) are gone. A comment at the call site records why, and what to do instead if
international numbers are ever supported (send `callingCode`, validate per-country
server-side — not reinstate a decorative picker).

Both apps lint clean, 0 errors. The two remaining warnings are pre-existing and on untouched
lines.

## 5. High — `errors.log` is 26 GB, fed by an infinite EPIPE loop

> **STATUS: CODE FIXED 2026-08-18** (not yet deployed). The loop and the unbounded growth are
> both closed. **Checking the production VPS disk is still outstanding and needs you** — see
> below.

```
-rw-r--r-- 1 ... 26623535802 Aug 12 05:54 logs/errors.log      # 26.6 GB
```

The tail shows the mechanism:

```
uncaughtException: EPIPE: broken pipe, write
  at console.error ... at logError (src/errorLogger.js:31) ... at process.<anonymous> (index.js:30)
```

`logError` writes with `console.error`. When stdout is a broken pipe that throws `EPIPE`, which
fires `uncaughtException`, whose handler is `logError` — which calls `console.error` again. The
loop only stops when the process dies, and writes gigabytes on the way.

The 26 GB file is a local dev artifact, but the same code runs on the VPS and the file is
**never rotated**. If it happens in production the disk fills, Supabase writes and the EnableX
call both start failing, and OTP breaks for *everybody* until PM2 restarts — recovering on its
own, leaving no obvious trace. That matches "sometimes it just stops working for a while".

### Fix

Guard the handler against re-entry, write to a stream with its own `'error'` listener rather
than `console.error`, and add `logrotate` (or PM2's `max_size`) for `logs/`. Check the VPS disk
now — this is the cheapest item here to verify and the most damaging to leave.

### What was actually done

`src/errorLogger.js`:

- **The `console.error` call is now wrapped.** It was the one call in `logError` that was not
  — `fs.appendFileSync` already had a try/catch — and it is the one that throws EPIPE. That
  single unguarded line is the whole loop.
- **Re-entry guard** (`inLogError`). `logError` is wired to `process.on('uncaughtException')`,
  so *any* throw from inside it re-enters it forever. The flag makes the loop structurally
  impossible regardless of which call starts misbehaving.
- **`installStreamErrorGuards()`**, called at the top of `index.js` before anything can log:
  attaches no-op `'error'` listeners to stdout/stderr so an EPIPE never becomes an
  uncaughtException in the first place. This is the root fix; the other two are defence in
  depth.
- **Rotation at 50 MB**, keeping one previous generation, so the logs are bounded at ~100 MB
  total with no external dependency.
- Corrected a stale comment claiming the disk was ephemeral and wiped on every deploy. That
  was true of Render; on the Hostinger VPS this file persists and grows without bound — which
  is precisely why nothing ever capped it.

**Verified**: reproducing the original condition (every `console.error` throws EPIPE) now
terminates after **1 attempt in 3ms** instead of looping. Rotation tested in an isolated copy:
under 50 MB appends without rotating; over 50 MB rotates and starts fresh; a second rotation
replaces the old generation so the total stays bounded. 3/3.

### Still outstanding — needs you

**Check the production VPS disk.** The code fix stops the log growing from here, but it does
not tell us whether the disk is *already* full, and a full disk breaks Supabase writes and the
EnableX call together — which looks exactly like OTP randomly failing for everyone and then
recovering on restart. There is no SSH host in `vps-deployment/scripts/` and no
`BUG_AGENT_TOKEN` locally, so this cannot be checked from the repo:

```
df -h
du -sh /path/to/astrowani-backend/logs
```

If `logs/errors.log` is huge there, truncating it is safe — it is a gitignored buffer, not an
archive.

**Production disk checked 2026-08-18: not an active problem.** `df -h` on the VPS reported
**9% used, 88 GB available**, so the loop never filled the production disk. The code fix keeps
it that way. (The backend's `logs/` is not under `/root/` on that box — worth locating once
with `find / -name errors.log` to confirm it is small.)

**Local dev machine, resolved 2026-08-18:** the new rotation code fired in place the first time
the backend ran, moving the 26 GB file to `errors.log.1` and starting a fresh log — a live
demonstration that the fix works. The rotated file was then deleted, reclaiming **25 GB**
(19 GB -> 44 GB free). Nothing reads `.1`; `bugAgentRoutes.js` reads only `LOG_FILE`.

## Secondary findings

| Finding | Detail | Impact |
|---|---|---|
| **Double-tap race** — **STATUS: FIXED 2026-08-18** (code not yet deployed) | Two concurrent requests both read `otp_codes` before either writes, so both pass `checkOtpSendThrottle` and both send. The `upsert` keeps only the *last* hash, so the **first-arriving SMS is invalid**. Fixed by making the send a compare-and-set (`otpStore.claimAndSet`): a fresh number is claimed with a plain `INSERT` (the primary key is the mutex, loser gets `23505`); an existing row is claimed with an `UPDATE ... WHERE last_sent_at = <value just read>` (loser matches 0 rows). The loser gets the normal `429 OTP_THROTTLED` shape and — critically — **no second SMS is sent**, which is the actual bug. See "What was actually done" below. | Was: user types the code that arrived first, gets "Invalid OTP", burns an attempt. Now: only one SMS goes out per race, and the loser is told to wait. |
| **`OTP_HMAC_SECRET` unset** | Falls back to `JWT_SECRET`. Rotating the JWT secret silently invalidates every in-flight OTP. | Latent; will look like a total OTP outage after a secret rotation. |
| **Per-IP limiter under CGNAT** | `httpHardening.js` allows 240 req/min per IP. Its comment claims "a CGNAT pool of ordinary users stays well under it" — but a CGNAT pool is thousands of devices, not one. Roughly 80 concurrent users on one Jio egress IP at 3 req/min reaches it. | Generic `429 Too many requests` for users who did nothing wrong — the same class of bug as the 2026-08-15 incident this file was written to fix. |
| **Delivery failures logged, never alerted** | `verifyEnxDelivery` writes `logError('enablex-sms', ...)` into the 26 GB file. Nothing reads it. | Every carrier-level drop is invisible. There is no way to answer "did this user's SMS actually get delivered". |
| **Global cap under-counts** | `isGlobalOtpCapExceeded` counts `otp_codes` rows, but rows are deleted on successful verify — so successful traffic is invisible to it. | Harmless at 20000, but the breaker does not measure what its comment claims. |
| **Dead OTP code paths** | `astrowani_vendors-main/src/utils/startOtpVerification.js` is a complete second OTP implementation via OTPLESS with a hardcoded app id (`XEI0EKAE23XPDNHKAQRJ`) — nothing imports it — but `otpless-react-native@^1.1.8` is **still a dependency in `astrowani_vendors-main/package.json`**, so the native SDK is compiled into the shipped vendor APK. `astrowani_customer-main/src/screens/OtpScreen/OtpScreen.js` is registered as a live route in `Navigation.js:154` but nothing navigates to it. | Confusion while debugging; an unused third-party auth SDK and its hardcoded app id shipped inside the vendor APK. Removing the dep also drops its native code and permissions from the build. |
| **No SMS autofill** | The DLT template `"Hi user, your OTP is {$var1} for Login on – Astrowaniindia"` carries no 11-character app hash, so Android SMS Retriever cannot autofill. | Every user hand-copies the code, which is where mistyping and expiry pressure come from. |

## Things that are correct and should not be undone

Worth stating explicitly, since much of this subsystem was hardened recently and the fixes
above must not regress it:

- OTPs are persisted in `otp_codes`, not an in-memory Map — survives `pm2 restart`. Verified:
  no plaintext OTPs and no NULL `otp_hash` rows remain in production.
- OTPs are HMAC'd, compared with `crypto.timingSafeEqual`, and generated with
  `crypto.randomInt` rather than `Math.random`.
- The 5-attempt verify cap works. Verified live: `attemptsRemaining` decrements correctly.
- EnableX's non-zero `result` in a HTTP 200 body is treated as a real failure, and the stored
  row is rolled back — so the app is no longer told "sent" for an SMS that never went.
- Throttling is per-number rather than per-IP, which is the right dimension under CGNAT.

## Recommended order of work

1. **Check VPS disk usage now** (finding 5) — one command, and it invalidates everything else if the disk is full.
2. **Normalize the phone number at both endpoints, and migrate existing rows** (finding 1) — the one that produces permanent, per-user, never-self-healing failure.
3. **Loosen and drain the send cap; don't count undelivered sends** (finding 2).
4. **Timeouts on both sides of the EnableX call** (finding 3).
5. **Remove or wire up the country picker** (finding 4).
6. Secondary findings, in the order listed.

Findings 1 and 2 together account for essentially all of the reported behaviour: 1 explains
"it doesn't work for certain people, ever", and 2 explains "it stops working after we keep
trying".

## Addendum 2026-08-18 — double-tap race fixed

Of the seven secondary findings, the double-tap race was the only one that produces a
user-visible OTP failure on its own, so it was fixed alongside findings 1–5 rather than left
open. See the secondary-findings table above for the mechanism and the fix.

**A defect surfaced during testing, and how it was closed.** `claimAndSet` throws on an
unexpected DB error — unlike the old fire-and-forget `upsert`, which swallowed everything —
and the endpoint had no outer `try/catch`, so an uncaught rejection would leave the request
hanging with **no response at all**: the exact dead-spinner failure mode this whole audit
exists to remove. Added a `try/catch` around the claim that returns a `503` instead. Confirmed
against a real fault: 6 concurrent requests against a local backend produced a genuine
`UND_ERR_CONNECT_TIMEOUT` to Supabase, which now surfaces as an honest `503` rather than a
hung connection.

**Verified** (local backend against the production database, `otp_codes` cleaned up after):

| Scenario | Result |
|---|---|
| 6 simultaneous requests, no existing row (cold start) | 1 winner (`200`), 5 losers (`429 OTP_THROTTLED`) |
| 6 simultaneous requests, existing row | 1 winner, 5 losers |
| Winner determined by number of `otp_codes` rows written | exactly 1 in both cases — i.e. exactly one SMS would go out |
| Request arriving just after a successful verify (row deleted) | falls through to `INSERT` and succeeds, not misread as a lost race |
| Full race suite, repeated | 7/7 passed |

The double-tap fix (`otpStore.claimAndSet` + the request-handler wiring + the `try/catch`) is
in `astrowani-backend/index.js`, same file and same not-yet-deployed status as findings 1–5.
Nothing here changes the "Recommended order of work" above — it rides along with finding 1
and 2's deploy.
